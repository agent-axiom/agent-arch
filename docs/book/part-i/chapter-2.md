# Глава 2. Референсная архитектура безопасного агента

!!! info "Как читать эту главу"
    Не пытайся запомнить названия всех слоев с первого прохода.

    Полезнее сделать три вещи:

    - проследить путь одного support-запроса;
    - увидеть, где у системы появляется право на действие;
    - выписать несколько обязательных слоев, без которых запрос нельзя безопасно довести до внешнего side effect.

## 1. Начнем не со слоев, а с одного живого кейса

Возьмем того же агента поддержки из первой главы.

Пользователь пишет:

> Я уже третий день жду активации доступа. Проверьте статус и создайте срочный тикет, если заявка застряла.

Если смотреть на задачу слишком упрощенно, может показаться, что дальше все очевидно:

- модель читает сообщение;
- выбирает нужный инструмент;
- проверяет статус;
- создает тикет;
- возвращает ответ.

Но production-система не может работать на такой схеме "в общих чертах". Слишком много важных вопросов остаются без ответа:

- кто именно просит действие;
- какие права у этого запроса;
- можно ли этому агенту вообще создавать тикеты;
- требует ли создание тикета подтверждения;
- какой контекст можно отправить в модель;
- что делать, если инструмент ответил частично или нестабильно;
- как потом восстановить всю цепочку при инциденте.

Именно из этих вопросов и рождается архитектура платформы.

## 2. Минимальная форма агента и почему ее мало

Полезно не пытаться удержать всю карту сразу. Сначала достаточно различать две вещи:

- минимальное ядро агентной системы;
- production-надстройку, без которой это ядро остается только прототипом.

Практический гайд OpenAI полезен тем, что начинает с очень простой формы: у минимальной agent system обычно есть три вещи.[^openai-practical]

- `model`
- `tools`
- `instructions`

Это хорошая стартовая рамка. Она полезна тем, что не дает сразу улететь в лишнюю сложность.

Но для production этого уже недостаточно. Как только у тебя появляются:

- доступ к внутренним системам;
- приватные данные;
- длинные сессии;
- write path;
- подтверждения;
- несколько команд и ролей,

минимальная тройка перестает быть архитектурой. Она остается только ядром, вокруг которого нужно строить платформу.

## 2.1. Что относится к runtime-архитектуре агента, а что нет

Здесь полезно провести еще одну границу, потому что команды очень часто смешивают runtime, обучение модели и product surface.

К runtime-архитектуре агента обычно относятся:

- `model`;
- `instructions`;
- `tools`;
- `memory`;
- planning routines или skills;
- `runtime`;
- guardrails и policies.

А вот несколько вещей к runtime-архитектуре обычно не относятся:

- training dataset и reward model принадлежат к разработке и обучению модели, а не к runtime;
- user interface относится к продуктовой поверхности, а не к ядру агентной логики;
- context window - это свойство выбранной модели, а не самостоятельный слой архитектуры.

Это различие кажется теоретическим, но на практике оно очень полезно. Если у команды начинает деградировать tool routing, approval path или retrieval discipline, причина обычно живет в runtime contour, а не в UI или в reward model.

## 3. Как один запрос должен проходить через систему

Посмотрим на тот же support-кейс уже как на архитектурный путь.

### 3.1. Входной слой

Сообщение не должно сразу попадать в модель. Сначала система превращает его в нормализованный запрос:

- кто пользователь;
- из какого tenant пришел запрос;
- какой канал входа;
- какой класс риска;
- какая сессия и какой `trace_id`;
- к какой политике будет привязан этот запуск.

Иными словами, в систему входит не "текст", а управляемый execution context.

### 3.2. Слой управления

Дальше система должна решить, что этому запуску вообще разрешено:

- какими моделями можно пользоваться;
- какие инструменты доступны;
- какие действия требуют подтверждения;
- какие лимиты действуют;
- что запрещено в текущей среде.

Это и есть control plane. Он отвечает не за "ум", а за право системы действовать.

### 3.3. Runtime

Потом запрос попадает в runtime, где выбирается паттерн выполнения:

- здесь достаточно обычного workflow;
- здесь нужен `single-agent loop`;
- здесь нужно прерывание на подтверждение;
- здесь запуск должен сохраниться в checkpoint и продолжиться позже.

Хороший runtime выглядит скучно. Он не поражает "магией", а делает ход выполнения предсказуемым.

### 3.4. Модельный слой

Только после этого в дело входит модель:

- получает отобранный контекст;
- делает следующий шаг;
- предлагает вызов инструмента или текстовый ответ;
- возвращает структурированный результат в runtime.

Важно не путать: модель может предлагать действия, но она не должна быть единственным местом, где решается, можно ли их исполнять.

### 3.5. Слой инструментов

Если агент хочет проверить статус заявки или создать тикет, он не должен ходить во внешний мир напрямую. Это делает tool gateway:

- проверяет policy decision;
- требует approval, если нужно;
- изолирует side effects;
- возвращает результат в runtime;
- пишет событие в трассу.

### 3.6. Трассировка и оценка

На каждом шаге система должна оставлять след:

- что модель решила;
- какой инструмент вызывался;
- какой policy gate сработал;
- было ли подтверждение;
- где выросла задержка;
- где возник сбой.

Без этого у тебя не платформа, а сложный черный ящик.

## 4. Теперь можно посмотреть на карту целиком

Если на этом месте карта кажется плотной, не пытайся запомнить названия всех блоков. Сначала достаточно ответить на три вопроса:

- где формируется execution context;
- где живет право на действие;
- где система оставляет достаточно следов для расследования и выпуска.

Ниже уже полезно показать платформу "видом сверху".

<div class="diagram-card">
<p>Референсная схема безопасной агентной платформы</p>

``` mermaid
flowchart TB
    user["Пользователь / API / Event"] --> interface["Interface layer"]
    interface --> identity["Identity & session layer"]
    identity --> control["Agent control plane"]
    control --> runtime["Orchestration runtime"]
    runtime --> cognition["Cognition plane"]
    runtime --> memory["Memory & knowledge plane"]
    runtime --> tools["Tool execution plane"]
    runtime --> telemetry["Telemetry & eval plane"]
    tools --> external["Внешние системы / MCP / SaaS"]
    memory --> stores["Vector DB / KB / profile memory"]
    control --> approval["Approval / policy / quotas"]
    telemetry --> audit["Traces / metrics / audit"]
```

</div>

Важно видеть в этой схеме не красоту слоев, а их роль:

| Слой | За что отвечает | Почему без него больно |
| --- | --- | --- |
| Interface layer | Чат, API, webhooks, события | Иначе каналы смешиваются с логикой исполнения |
| Identity and session layer | Пользователь, сервисный аккаунт, tenant, request scope | Иначе ломаются IAM, аудит и изоляция |
| Agent control plane | Политики, approvals, лимиты, каталоги | Иначе система действует без управляемости |
| Orchestration runtime | Workflow graph, planner, checkpoints | Иначе выполнение разваливается при первом усложнении |
| Cognition plane | Model router, prompt assembly, validators | Иначе модель становится "центром мира" |
| Memory and knowledge plane | Состояние, память, retrieval | Иначе контекст бесконтрольно разрастается |
| Tool execution plane | Gateway, sandbox, side-effect isolation | Иначе blast radius слишком велик |
| Telemetry and eval plane | Traces, metrics, datasets, regression gates | Иначе качество нельзя измерять и расследовать |

## 5. Пять опор production-платформы

Свежие материалы Google Cloud полезны тем, что предлагают еще одну удобную рамку: не "один умный агент", а пять опор production-платформы.[^google-five-pillars]

- `framework`
- `model`
- `tools`
- `runtime`
- `trust`

Эта рамка полезна по очень практической причине. Она быстро отрезает самообман.

Если у тебя есть только:

- сильная модель;
- хороший prompt;
- пара инструментов,

но нет `runtime` и `trust`, у тебя еще не платформа. У тебя прототип.

## 6. Какие архитектурные решения нужно принять явно

Уже на ранней стадии полезно принять несколько решений не "по ходу дела", а явно.

### 6.1. Какие слои контекста существуют

Google правильно дисциплинирует prompt assembly через context layers.[^google-agent-overview][^google-govern]

Обычно достаточно явно развести:

- `static context`: роль, policies, allowed capabilities, fixed instructions;
- `session context`: то, что живет в рамках сессии;
- `turn context`: то, что относится только к текущему запросу;
- `cached context`: то, что стоит подмешивать выборочно.

Практическое правило простое: в prompt должны попадать не все доступные данные, а только данные с понятным назначением и сроком жизни.

### 6.2. Где проходит право на действие

У модели не должно быть права напрямую исполнять внешний side effect.

Право на действие должно жить в сочетании:

- policy engine;
- approval logic;
- tool gateway.

Именно поэтому control plane так важен: он отделяет "модель предложила" от "система имеет право сделать".

### 6.3. Когда делить систему на несколько агентов

Практический гайд OpenAI правильно не романтизирует `multi-agent` как default choice.[^openai-practical]

Обычно разделение оправдано, когда:

- одному run уже тесно в одном контексте;
- подзадачи требуют разных инструментов и guardrails;
- ownership делится между командами;
- параллелизм действительно уменьшает latency или cognitive load.

Если этих признаков нет, один агент с хорошим workflow graph почти всегда проще и надежнее.

## 7. Что нельзя смешивать в одну кучу

Есть минимум четыре вещи, которые стоит различать с самого начала:

- **short-term state**: текущее состояние выполнения;
- **long-term memory**: факты, профили, эпизоды;
- **retrieval**: доступ к внешним знаниям;[^langgraph-memory]
- **tool execution**: реальные действия во внешнем мире.

Пока система маленькая, это разделение может казаться бюрократией. После первого серьезного инцидента оно начинает выглядеть как инженерная гигиена.

## 8. Минимальный кодовый принцип

Если хочется увидеть всю идею в очень сжатом виде, шаблон выглядит так:

```python
from dataclasses import dataclass


@dataclass
class ToolRequest:
    tool_name: str
    actor_id: str
    risk_class: str
    payload: dict


def execute_tool(request: ToolRequest, policy_engine, approval_service, gateway):
    decision = policy_engine.evaluate(request)
    if not decision.allowed:
        raise PermissionError(decision.reason)

    if decision.requires_approval:
        approval_service.require_human_signoff(request, decision)

    return gateway.call(request.tool_name, request.payload)
```

Смысл здесь один: модель может предложить действие, но право на исполнение живет не в модели, а в gateway и policy слое.

## 9. Что нужно вынести из этой главы

Если кратко, хорошая агентная платформа держится на нескольких скучных, но очень ценных вещах:

- явный входной контекст;
- control plane;
- отдельный runtime;
- отдельный tool gateway;
- отдельные traces и evals;
- approvals там, где они действительно нужны.

Архитектура полезна не потому, что делает схему красивой. Она полезна потому, что не дает системе рассыпаться при первом реальном усложнении.

## 10. Что делать сразу после этой главы

Если ты проектируешь агентную систему прямо сейчас, зафиксируй хотя бы это:

1. Где именно у тебя входной execution context?
2. Где живет право на действие?
3. Какой runtime pattern у тебя выбран первым?
4. Какие side effects идут только через gateway?
5. Какие поля команда должна видеть в трассе с первого дня?

Если эти вещи уже описаны, у тебя начинает появляться архитектура. Если нет, у тебя пока только идея агента.
