# С чего начать

Если ты впервые попал в эту книгу, начни с одного вопроса: тебе нужен впечатляющий демо-агент или система, которая выдержит реальность production?

Эта книга написана для второго случая. Ее полезно читать как один аргумент о том, как агентные системы взрослеют: от prompt-heavy прототипов к управляемым системам с границами доверия, policy layer, approvals, observability, evals и жизненным циклом.

Агентов строить скучно, но результат ошеломляющий: дисциплина вокруг trust boundaries, traces, approvals и rollout превращает демо в систему, которую можно безопасно улучшать.

Эта страница нужна для одного: быстро выбрать маршрут чтения.

## Если читать только одно

Если нужен самый короткий вход в идею книги, прочитай [Главу 1. Почему агенту нужна платформа, а не магия](book/part-i/chapter-1.md).

Там формулируется главный тезис: production agent system нельзя строить как “модель плюс набор tools”. Ее приходится проектировать как управляемую операционную систему.

## Что это за книга

Это не руководство по одному фреймворку и не каталог AI-возможностей. Это практическая архитектурная книга для команд, которым нужно запускать агентов в реальной среде, где есть write paths, человеческие подтверждения, границы доступа, телеметрия, оценки и явная эксплуатационная ответственность.

После этого маршрута у тебя уже должна сложиться рабочая рамка:

- где у агента проходят реальные trust boundaries;
- как выглядит безопасное исполнение инструментов;
- почему одной “умной модели” мало без traces, SLO и evals;
- что требуется до первого серьезного rollout.

!!! example "Если хочешь идти по сквозному кейсу"
    Следи за историей support-triage: она начинается с retrieval и safe tool execution, проходит через duplicate-ticket recovery, traces, SLO и eval gates, а затем доводится до rollout, ADLC, assurance, provenance, retirement, misalignment controls, telemetry и registry. Это хороший маршрут, если хочется увидеть не абстрактные слои, а один incident-to-platform-contract путь.

!!! note "Canonical case routes"
    Для проверки покрытия держи рядом три canonical cases. **Support triage** ведет через write capabilities, approvals и duplicate-ticket recovery. **Internal knowledge assistant** подсвечивает retrieval, memory, freshness и knowledge provenance. **Incident coordination** проверяет traces, escalation, notification side effects, response ownership и post-incident learning.
