## 2. Повторяемый формат практикума

Для следующих книжных расширений использовать одинаковую структуру, чтобы главы развивались не хаотично, а как практическое руководство:

1. Проблема: что ломается в production, если команда не проектирует этот контур явно.
2. Контракт: какие сущности и поля должны быть названы до реализации.
3. Пошаговый дизайн: 6-10 инженерных шагов, которые можно пройти на одном агентном сценарии.
4. Минимальная схема: YAML, JSON или псевдокод, который делает решение проверяемым.
5. Failure modes: пустой, слабый, конфликтующий, запрещенный или устаревший путь.
6. Traceability: какие события и поля должны остаться в трассе.
7. Canonical cases: как решение проверяется на support triage, internal knowledge assistant и incident coordination.
8. Review checklist: короткий список вопросов для архитектурного ревью.
9. Implementation impact: что должно измениться в коде, конфигурации, evals или operational artifacts.

Этот формат важен для IT-книги: он переводит главу из объяснения в рабочую процедуру, которую читатель может применить к своей системе.

## 3. Карта зрелости рукописи

Оценка верхнеуровневая. Она не про стиль, а про книжную полноту: есть ли у главы аргумент, практический сценарий, проверяемый артефакт и связь с эксплуатацией.

| Зона | Текущая зрелость | Что уже работает | Что нужно усиливать дальше |
| --- | --- | --- | --- |
| Front matter | Средняя | Есть аннотация, аудитория, предисловие, блок об авторе с пропусками | Финальная авторская биография, издательский тон, единая терминологическая рамка |
| Части I-II | Средняя | Задан язык агентной архитектуры и безопасности | Больше сквозных кейсов, меньше сжатых переходов между концепциями |
| Часть III: память и знания | Выше средней | Память, типы памяти, retrieval/context получили практические блоки | Нужна финальная стыковка с evals и reference package |
| Часть IV: выполнение и инструменты | Средняя | Есть модель tool gateway, MCP, idempotency | Нужны практикумы по sandbox profile, tool contract review и rollback boundary |
| Часть V: observability/evals | Средняя | Есть trace, SLO, evals | Нужен единый evidence spine и практикум по расследованию слабого eval-сигнала |
| Части VI-VII: ADLC, rollout, incident response | Средняя | Есть жизненный цикл, rollout и production checklist | Нужны более плотные case-study вставки и decision records |
| Часть VIII и приложения | Неравномерная | Есть много полезных схем и справочных материалов | Требуется редакторская навигация: что читать как appendix, что поднять в основной текст |
| Reference package linkage | Средняя | Есть связь с `agent_runtime_ref` и схемами | Нужны более явные "из текста в код" мосты после ключевых практикумов |

## 4. Приоритеты следующих смысловых итераций

2. `Глава 9. Песочница выполнения и MCP как интеграционный контракт`: добавить практикум по sandbox profile и boundary between host/client/server.
3. `Глава 10. Идемпотентность, повторы, лимиты запросов и границы отката`: добавить практикум по side-effect safety и rollback playbook.
4. `Глава 11. Трассы, спаны и структурированные события`: добавить практикум по trace event catalog для одного сквозного сценария.
5. `Глава 13. Офлайн-оценки, онлайн-оценки и регрессионные шлюзы`: добавить практикум по eval gate для retrieval/tool failures.
6. `Глава 18. Чеклист промышленного запуска`: превратить часть чеклиста в production readiness review template.

## 5. Верхнеуровневое выравнивание после текущего прохода

После добавления блока по сборке контекста логическая последовательность части III стала сильнее:

1. зачем память опасна;
2. какие типы памяти нужны;
3. как память возвращается в контекст;
4. как проверить, что контекст собран разрешенно и объяснимо;
5. как дальше перейти к инструментам и выполнению.

Оставшийся структурный риск: часть IV теперь должна получить такой же практический уровень. Иначе переход от context/retrieval к tool execution будет ощущаться как переход от готовой процедуры к более сжатому конспекту.
