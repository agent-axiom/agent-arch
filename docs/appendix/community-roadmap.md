# Дорожная карта для сообщества

У книги уже есть сильная база: архитектура, безопасность, память, выполнение, наблюдаемость, организационная модель и runnable reference package. Поэтому ниже не общий wishlist, а backlog **следующего слоя пользы**.

## Что уже сделано

- страница [С чего начать](../start-here.md);
- [многоязычный глоссарий](glossary.md);
- [набор шпаргалок](cheat-sheets.md);
- набор [практических кейсов](case-studies.md);
- страница [шаблонов политик](policy-templates.md);
- опорный пакет и его [документация](reference-package.md);
- reference schemas для трасс, оценок, политик, подтверждений, памяти, rollout и lifecycle artifacts;
- отдельная страница про [стек публикации](stack.md).

## Как я отбираю следующие шаги

Каждый пункт ниже проходит по трем критериям:

- его можно быстро применить в реальной работе;
- он полезен не только автору книги, но и внешнему сообществу;
- он повышает международную читаемость проекта, а не только глубину текста.

## Следующие 10 улучшений

### 1. Расширение набора case studies

Текущие кейсы уже полезны, но стоит добавить еще 2-3 сценария:

- enterprise workflow agent;
- CRM/task agent;
- security-sensitive assistant.

Почему это важно: чем больше у читателя узнаваемых сценариев, тем легче применить архитектуру к своей системе.

### 2. Расширение набора policy templates

В книге уже есть первые примеры, но сообществу нужны более явные шаблоны:

- tool approval policy;
- memory write policy;
- egress policy;
- rollout gate policy;
- retrieval policy.

Почему это важно: шаблон, который можно взять и адаптировать, ценнее длинного текста о том, почему шаблон нужен.

### 3. Более богатые trace examples и визуальный QA

Trace schema и event catalog уже есть. Следующий шаг — сделать их проще для проверки и чтения:

- добавить более реалистичные JSONL trace examples;
- показать successful run, approval wait, denied run и failed run;
- держать rendered schema pages свободными от сломанных таблиц, склеенных списков и raw diagram blocks;
- добавить легкий rendered-site QA checklist для самых видимых страниц.

Почему это важно: observability становится сильнее, когда у сообщества есть не только общий каркас событий, но и конкретные примеры того, как он выглядит на опубликованном сайте.

### 4. Расширение `agent_runtime_ref` реальными сценариями

Пакет уже полезен, но следующим шагом стоит добавить:

- один knowledge scenario;
- один high-risk scenario с approval;
- один denied-by-policy scenario;
- примеры JSONL traces в docs.

Почему это важно: runnable reference package должен быть не просто демонстрацией happy path, а учебным набором production-like сценариев.

### 5. Contribution kit для сообщества

Нужно облегчить внешний вклад:

- страница `How to contribute patterns`;
- шаблон для нового case study;
- шаблон для нового glossary entry;
- шаблон для нового policy template.

Почему это важно: хороший open handbook растет быстрее, когда у людей есть понятный формат, как именно помогать проекту.

### 6. Усиление внутренних ссылок и chapter journeys

Нужно усилить связки между главами:

- более явные переходы "что читать дальше";
- ссылки между архитектурой, кейсами и шаблонами;
- короткие decision paths внутри частей.

Почему это важно: книга становится полезнее, когда читатель не теряется между сильными, но плотными разделами.

### 7. SEO и discoverability слой

Нужен системный слой discoverability:

- glossary;
- cheatsheets;
- более явные internal links между главами;
- social preview assets;
- structured landing copy для `ru/en/zh`.

Почему это важно: даже сильная книга не работает на сообщество, если ее трудно найти, понять и переслать другим.

### 8. Social and sharing assets

Нужны аккуратные артефакты для распространения:

- social preview assets;
- несколько shareable cheat sheets;
- короткие landing summaries для `ru/en/zh`.

Почему это важно: у книги выше шанс на международный охват, когда ее удобно не только читать, но и пересылать.

## Что делать первым

Если выбирать только ближайшие 3 шага, я бы делал так:

1. Более богатые trace examples и visual QA
2. Contribution kit
3. Расширение набора case studies

Это даст самый быстрый рост пользы для сообщества и не потребует переписывать архитектурные главы.

## Что даст наибольший эффект через месяц

Если довести backlog до следующего уровня, то через месяц у проекта появятся:

- более понятный вход для новых читателей;
- больше цитируемых страниц;
- больше reusable материалов для команд;
- более ясный формат внешнего вклада;
- более сильный международный профиль проекта.
