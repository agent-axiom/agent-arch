# Практические кейсы

Эта страница нужна для простого вопроса: как вся книга выглядит не на уровне абстракции, а на уровне живой системы.

Ниже три сценария, в которых архитектурные слои, guardrails и orchestration choices уже можно обсуждать как инженерные решения, а не как красивые слова.

## Кейс 1. Support triage agent

### Что делает система

Агент принимает входящий запрос клиента, собирает контекст, проверяет историю обращений и выбирает безопасный следующий шаг:

- ответить сразу;
- запросить уточнение;
- завести тикет;
- эскалировать человеку.

### Почему здесь агент вообще нужен

Здесь агент оправдан, потому что:

- входящие сообщения неструктурированы;
- решение зависит от сочетания текста, истории клиента и политики;
- path не всегда фиксированный, но и не требует полной автономии.

То есть это хороший кандидат на `workflow + guarded agent loop`.

### Рекомендуемая схема

- один основной triage agent;
- read-heavy tools для customer profile и ticket history;
- write tool только для `create_ticket`;
- approval boundary для чувствительных действий;
- structured decision output на каждом run.

### Главные риски

- prompt injection через письмо клиента;
- утечка соседнего tenant context;
- лишний write action при нестабильной интеграции;
- слишком широкая свобода у triage agent.

### Что особенно важно в архитектуре

- жестко отделять instructions от текста клиента;
- не давать agent прямой доступ в helpdesk API;
- хранить stop conditions у triage routine;
- логировать все write intents и approvals.

## Кейс 2. Internal knowledge agent

### Что делает система

Этот агент помогает сотрудникам находить знания в документации, runbooks, тикетах и внутренних wiki-страницах.

Он:

- понимает вопрос;
- делает retrieval;
- собирает grounded answer;
- показывает источники;
- при низкой уверенности не выдумывает, а честно ограничивает ответ.

### Почему здесь часто хватает одного агента

В этом кейсе многие команды слишком рано уходят в multi-agent. Обычно это не нужно.

Чаще всего хватает:

- одного agent loop;
- хорошего retrieval pipeline;
- отдельного policy layer;
- строгой маркировки untrusted content;
- quality gates на answer generation.

### Главные риски

- retrieval noise;
- доступ к документам не по роли;
- leakage из приватных knowledge zones;
- галлюцинации при слабом grounding.

### Что особенно важно в архитектуре

- tenant- и role-scoped retrieval;
- short-term state отдельно от long-term memory;
- цитаты и source references в output;
- traces по retrieval и answer assembly.

## Кейс 3. Incident coordination agent

### Что делает система

Агент помогает в инциденте:

- собрать сигнал из мониторинга;
- обогатить его контекстом;
- создать incident thread;
- предложить следующий runbook шаг;
- передать задачу нужной роли.

Это уже не "chat assistant", а operational system component.

### Почему здесь особенно важна orchestration discipline

Здесь легко ошибиться и либо:

- сделать одного перегруженного manager agent;
- либо слишком рано уйти в handoffs, в которых теряется ответственность.

Обычно хороший старт такой:

- manager pattern на intake и координации;
- handoff только там, где реально начинается другая role boundary;
- все write actions проходят через capability contracts.

### Главные риски

- ложная уверенность при noisy alerts;
- повторные side effects;
- потеря audit trail во время handoffs;
- слишком широкие runtime permissions.

### Что особенно важно в архитектуре

- единый trace на весь incident run;
- explicit ownership на каждом handoff;
- idempotency для ticketing и notifications;
- human approval для risky remediation actions.

## Как использовать эти кейсы

Лучше всего читать их не подряд, а как карту:

- сначала выбрать кейс, похожий на твою задачу;
- потом пройти по связанным главам;
- потом вернуться и проверить, не переусложняешь ли ты свой дизайн.

Если книга будет полезна сообществу, именно такие страницы должны со временем расти быстрее всего: они превращают архитектуру в инженерную опору.
